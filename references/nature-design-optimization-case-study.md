## Round 1：组件决策树 + 扩展指南 + 响应式模板

**目标维度**：dim5（可执行性）+ dim8（实测表现）

**改进内容**：
1. 新增「组件选择决策树」（3 层：页面类型 → 特殊组件 → 状态检查）
2. 新增「非标准组件扩展指南」（4 个常见扩展组件 CSS 模板：仪表盘/步骤指示器/滑块/弹窗）
3. 新增「响应式断点实现模板」（Mobile-First 完整代码 + 5 条响应式规则）

## Round 3b：体积压缩（紧急修复）

**触发条件**：SKILL.md 体积达 178.1%（693/389 行），超过 150% 限制。

**压缩策略**（内容零损失）：
1. **CSS 代码块压缩**：4 个扩展组件模板从多行压缩为单行规则（Gauge/Stepper/Slider/Modal），节省 ~60 行
2. **反例示例表格化**：4 个独立代码块反例合并为 1 个 4 行表格，节省 ~30 行
3. **HTML 模板精简**：删除冗余注释和空行，节省 ~15 行
4. **SVG 模板去注释**：删除 2 行 HTML 注释

**结果**：693 行 → 582 行，**149.6%**（符合 <150% 限制）

**关键教训**：
- 优先压缩 CSS 代码块（删除换行/缩进，改为单行规则），而非删除内容
- 反例示例用表格横向对比 ❌/✅，比独立代码块更省空间且可读性更好
- 体积检查应在每轮 commit 前执行，而非最后才发现

## 合并后体积反弹（意外教训）

**触发条件**：合并 feature 分支到 master 后，体积从 149.6% 反弹到 **155.8%**（606/389 行）。

**根因分析**：
- git merge 使用 ort 策略（三方合并），feature 分支和 master 的 common ancestor 是初始 commit
- feature 分支有大量新增内容，master 也有新增（results.tsv/test-prompts.json）
- merge 后的 SKILL.md 包含了 feature 分支的所有改动，但 git 的合并算法不会自动压缩已压缩的内容
- 实际上是因为 feature 分支在 Round 3b 压缩后，又新增了 Round 4 的预览框架章节（~20 行），合并时这些新增行被完整保留

**处理**：
- 当时未在合并后立即检查体积
- feature 分支已删除，无法回滚
- 当前 master 体积 155.8%，**超过 150% 限制**

**教训**：
1. **合并后立即执行体积检查**：`wc -l SKILL.md && python3 -c "n=open('SKILL.md').read().count(chr(10)); print(f'{n/original*100:.1f}%')"`
2. **若超标，直接在 master 精简**（压缩 CSS/表格化反例），不再开新分支
3. **删除 feature 分支前确认体积合规**
4. 将体积检查加入 Phase 3 汇总报告的标准步骤

## 可复用模式

### 模式 A：组件选择决策树
适用于任何「根据用户意图匹配技术方案」的 skill（前端组件、数据分析工具、API 选择等）。

三层结构：
1. **第一层**：识别场景类型（关键词 → 类型映射）
2. **第二层**：识别特殊需求（关键词 → 扩展组件映射）
3. **第三层**：状态覆盖检查清单（勾选清单确保完整性）

### 模式 B：体积压缩策略
当 SKILL.md 体积接近 150% 限制时：
1. 优先压缩 CSS/代码块（删除换行，改为单行规则）
2. 反例示例表格化（横向对比 ❌/✅）
3. 删除 HTML/SVG 中的注释行
4. 合并相邻的短段落

### 模式 C：三段式异常处理
把「场景/触发条件/处理动作」两列表升级为「触发条件 / 一线处理 / 仍失败兜底」三段式。适用于任何需要 robust 异常处理的 skill。

### 模式 D：多页面预览框架
适用于生成多个 HTML 原型的 skill：
1. 提供 `preview-shell.html` 模板（iPhone 手机壳 + 右侧控制面板）
2. 交互注释规范：核心交互/业务规则/状态机/数据展示
3. 配置区驱动：修改 `PAGES` 数组和 `ANNOTATIONS` 对象即可
