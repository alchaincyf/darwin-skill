## 逐项来源

### ACES：读文档的分数预测不了实跑效果

Kevin等（NVIDIA），*Evaluating Skills, Not Just Agents: Agentic Continuous Evaluation of Skills*，arXiv:2608.20614，2026-08-20。

- 145个真实skill上，确定性结构分与LLM读评分的Spearman相关系数只有0.14；两种读文档的方法彼此都不一致。
- 结构分、LLM读评分与实跑增益的相关系数分别是−0.0181和−0.0266。作者的解读是这些分数不构成有用的运行时代理指标，不是负相关。
- 增益的量法：同一任务、同一harness、同一模型，带skill和不带各跑一次，取成对差值（Skill Lift）。947个成对样例里，689个为正，171个为零，87个为负。
- 固定harness换更强的模型后，基线上升，增益缩小，而绝对成绩仍然很高。只看绝对成绩会以为skill还在起作用。
- 每次配对运行都保留配置好的辅助skill和干扰skill，目标skill要在它们中间被选中才算数。可见skill从1个加到20个，平均耗时从258秒升到451秒。测触发要把同环境的其他skill放进去。

### Skill Issue：给文档打分的指标会选出最差的文档

Kozyrev等（JetBrains Research），*Skill Issue: Lessons from Optimizing Repository SKILLs for Coding Agents*，arXiv:2609.12742，2026-09-11。

- 他们试了多种打分方式。按「文档事实多不多」「看起来是否完整、是否有操作感」选出的文档，在留出任务的该项得分上升，agent的行为却没有变好；其中按完整度选出的那份，在所有看行为的指标上是全组最差。
- 他们最后只保留成对比较：同一任务上，带这份文档的agent是否比带种子文档的做得更好。
- 每个仓库20到26条留出任务时，几个百分点的提升无法和agent自身的运行波动区分开。所以达尔文的报告必须写明测试条数，并承认只能发现大差异。
- 仓库维护者审读优化后的文档：两份都含有只有在项目里干过才知道的知识，也都掺了agent用不着的通用建议。
- 按通过数优化的版本，会把训练用的那几个任务直接写进文档，换一批任务就没用。这是留出集要防的事。

### SkillsBench：精简的skill有用，面面俱到的没用

Li等，*SkillsBench: Benchmarking How Well Agent Skills Work Across Diverse Tasks*，arXiv:2602.12670。

- 人工整理的skill把平均通过率从33.9%提到50.5%。
- 模型自己生成的skill，在三个主流harness上比不带skill低8.1到11.5个百分点。
- 按篇幅分：精简型+19.0，标准型+21.5，详尽型+14.5，面面俱到型+0.7。
- 87个任务里有13个，带skill反而更差。
- 作者的建议：skill应该写验证环节会卡、而agent自己推断不出来的细节，不追求完整。

### SkillOpt：留出集上严格更好才接受

Yang等（Microsoft Research等），arXiv:2605.23904。

- 数据分成训练、选择、测试三份。候选改动只有在选择集得分严格高于当前版本时才接受，平局拒绝。
- 被拒绝的改动进入缓冲区，供后续反思使用。达尔文对应的做法是把回滚的假设记进results.tsv，下次先读。
- 每步改动数量有上限。去掉这个上限，三个基准上的成绩都下降。

### SSO：没有标准答案时，用成对比较执行结果

Peng等（中科院自动化所等），*Self-Supervised Skill Optimization*，arXiv:2607.28777，2026-07-30。

- 没有标注和评分器时，用LLM评委成对比较两版skill的执行结果（答案、轨迹、产物）来驱动优化，新版在未标注的验证集上胜出才接受。
- 为减轻位置偏差，随机化两份结果的呈现顺序。
- 平局不计入任何一方。

### 138K：路由缺陷最常见，越长缺陷越多

Zhang等，*What Keeps Agent Skills from Being Reusable? Evidence from 138K SKILL.md Files*，arXiv:2608.08453。

- 67.0%的skill至少有一处路由元数据缺陷，52.3%没写触发指引。
- 检索压力测试里，路由无缺陷的skill首位命中88.5%，有缺陷的82.6%。
- 缺陷密度随篇幅上升（Spearman 0.508）：超过500行的平均4.76处，50行以内的1.48处。
- 建议description前置使用场景、控制在250字符内。达尔文的体检脚本取了其中可以确定性检查的部分。

### Anthropic：skill编写指南与skill-creator

- 编写指南（platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices）：默认模型已经很聪明，只写它不知道的；约束松紧跟任务的脆弱程度走；正文不超过500行；引用只下沉一层；先建评测再写文档。
- skill-creator：带skill与基线同时跑、检查项评分、盲评比较器；description优化时把触发请求按六四分成训练和留出，每条跑3次。

### 本项目自己的记录

- 2026-09-12，一个手机自动化skill：三位读文档的评委3比0判更好，上真机后跟进轮走错入口，多绕33次工具调用。同日另一轮，评委2比1判更好，投反对的那位读了引擎源码，指出新流程第2步必被拦下，本地实跑证实。
- 2026-08-25，评测17个外部skill时，评委把候选仓库自带的脚本判成虚构、裸跑组实际调用了runtime内置skill，修正后两条结论翻转。
- 2026-09-22，被测agent读了同目录的对照稿，产出里出现几十处10字以上的逐字重合，该组盲评作废。
- 2026-11-14，3.0发布前在huashu-excel副本上试跑：带skill对裸跑1胜1平0负；把253行报告制作细节下沉后，新版对原版1胜1平0负、体积−31%，保留。试跑抓出协议的三个漏洞（执行者能读到测试文件、执行记录和路径暴露来历、带检查点的skill等不到用户），已修。只跑了2条开发集，未跑留出集。
- issue #18：一个表单自动化skill用问答题测得8.5分，换成带真实数据的端到端测试才暴露5处文档没写到的操作缺口。

## 和skill-creator的评测相比

| | skill-creator | 达尔文3.0 |
|---|---|---|
| 带skill对基线实跑 | 有 | 有 |
| 盲评 | 可选的进阶项 | 每次裁决必做，逐评委逐测试随机顺序 |
| 保留还是回滚 | 人看结果后决定 | 脚本按固定规则裁决，再交人审 |
| 平局 | 无规则 | 平局归短的那版 |
| 留出集 | 只用于description优化 | 正文改动也要过留出集 |
| 事实性指控 | 无规则 | 先验证，事实大于票数 |
| 触发测试 | 只看目标skill | 带邻居skill一起测 |

| 模型升级后回归 | 无 | 复测模式 |

这张表只比评测方法。skill-creator还负责从零创建skill、带结果查看器，那些不是达尔文要做的事。

## 已知的局限

- 每个skill只有几条测试，只能发现大差异。小改进会被运行波动淹没，这类改动在3.0里会被判平并回滚，这是有意的取舍。
- 评委仍是LLM。成对比较和随机顺序能抵消一部分偏差，抵消不了全部。
- 触发测试是模拟的，和各runtime真实的加载逻辑有出入。
- 以上论文多数在编码和数据类任务上做的实验，写作、设计这类主观skill的证据更少。
