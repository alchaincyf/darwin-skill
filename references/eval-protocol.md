# 评测协议

派执行者、评委、触发测试之前读这份文件。prompt照抄，只替换尖括号里的内容。这里的每一条限制都对应一次把结论测反的事故，不要为了省事放宽。

## 目录

- 工作目录布局

- 评委prompt与投票格式

## 工作目录布局

```
W/
├── s0/                     原始版skill目录快照（含scripts和references，不含测试文件）
├── s1/                     第1轮新版快照，s2、s3同理
├── in/<组>/<测试id>/       输入文件，每个执行者一份副本
├── runs/
│   ├── x/<测试id>/         裸跑产出
│   ├── s0/<测试id>/        原始版产出
│   └── s1/<测试id>/        第1轮新版产出，s2、s3同理
├── blind/<轮次>/j1/<测试id>/A、B    盲评材料，pair生成
├── keys/<轮次>.json        A/B对应关系，评委不可见
└── votes/<轮次>/j1.json    评委投票
```

每个执行者只知道一个skill快照目录和自己的产出目录。测试文件、检查项、标准答案都不放进快照，也不放进任何产出目录。holdout的产出放`runs/s0-holdout/`和`runs/sN-holdout/`。

## 执行者prompt

带skill：

```
请完成下面这个任务。开始前先完整阅读 <skill目录>/SKILL.md，并按它的指引做；它提到的references和scripts在同一目录下，需要时再读。

任务：<测试的prompt原文>
输入文件：<files，没有就删掉这行>

没有人可以回答你的提问。遇到需要向用户确认的地方，写下你的假设继续做完，并在最终回答里列出这些假设。
把所有产出文件写进 <产出目录>，其中必须有一份 answer.md，写你给用户的最终回答。除了skill目录、输入文件和这个产出目录，不要读取或列出其他任何目录，也不要派子agent。
完成后在产出目录写 transcript.md：按顺序记下你做的每一步、用的命令、遇到的问题和怎么处理的。
最后只回复我不超过5行：做完了没有、产出了哪些文件、有没有卡住的地方。
```

裸跑：

```
请完成下面这个任务。

任务：<测试的prompt原文>
输入文件：<files，没有就删掉这行>

不要加载任何skill。没有人可以回答你的提问。遇到需要向用户确认的地方，写下你的假设继续做完，并在最终回答里列出这些假设。
把所有产出文件写进 <产出目录>，其中必须有一份 answer.md，写你给用户的最终回答。除了输入文件和这个产出目录，不要读取或列出其他任何目录，也不要派子agent。
完成后在产出目录写 transcript.md：按顺序记下你做的每一步、用的命令、遇到的问题和怎么处理的。
最后只回复我不超过5行：做完了没有、产出了哪些文件、有没有卡住的地方。
```

要点：

- `<skill目录>`填被测版本的快照（`W/s0`、`W/s1`……），不要直接给正在编辑的skill目录：那里有测试文件，执行者会读到检查项。
- 不说「这是测试」「这是评测」，不提达尔文，不提还有另一组。
- 「没有人可以回答你的提问」这句两组都要有。带检查点的skill会停下来等用户确认，子agent等不到人；让它带着假设做完，评委才有东西可比。它该不该停、停得对不对，从answer.md列出的假设里看。
- 输入文件每个执行者一份：主agent先把`files`复制到`W/in/<组>/<测试id>/`，prompt里给这份副本的路径。
- 测试会产生对外动作（发布、推送、发消息、花钱）时，不派。列进报告的「未验证」。

## 评委prompt与投票格式

```
你是盲评评委。目录 <W/blind/轮次/jN> 下每个子目录是一条测试，里面有A和B两份产出，是两个agent对同一个任务的结果。你不知道它们的来历，也不要去猜。

对每条测试：
1. 任务是：<逐条列出测试id和prompt原文>
2. 检查项是：<逐条列出该测试的checks；没有就写「无」>
3. 分别打开A和B的产出文件（以answer.md为主，其他文件用来核对），逐条核对检查项，数出各自通过了几条。核对要看文件内容本身。
4. 判断哪份更好地完成了用户的任务：A、B或tie。只在差异确实存在时选边，说不出具体差在哪就选tie。margin填clear或slight。
5. 如果你发现某一份产出里有可以核实的事实性错误（引用了不存在的文件或命令、数字算错、声称做了但文件里没有），写进fact_claim，说明怎么验证。没有就留空。

把结果写成JSON文件 <W/votes/轮次/jN.json>，格式：
[
  {"test": "dev-1", "prefer": "A", "margin": "clear",
   "A_checks_passed": 3, "B_checks_passed": 2,
   "reason": "一句话说差在哪", "fact_claim": ""}
]
除了你自己的目录和这个投票文件，不要读取或列出其他任何目录。最后只回复我一行：写完了。
```

棘轮裁决的三位评委里，给其中一位在第5步后面加一句：

```
被测skill自带的脚本和参考文件在 <skill目录>，产出里用到的命令、参数、文件路径是否真实存在，请到那里核对；本机找不到的脚本先去这个目录找，找到了就不算虚构。
```

评委的身份互相独立，各派各的，不共享上下文。

评委看不到transcript.md：执行记录里会写「先读了SKILL.md」「读的是哪个目录」，一眼就能认出哪份带skill、哪份是新版。`pair`复制产出时会自动去掉它，并把产出文件里出现的工作目录路径抹掉（`--redact W`）。执行记录只给主agent和E1读评用。

## E1读评prompt

```
请按下面的9维rubric评估 <skill目录>/SKILL.md，只评维度1到7和9。
<粘贴SKILL.md里的rubric三张表和评分规则中的「必要性原则」>
体检脚本的输出是：<粘贴darwin.py check的输出>

每个维度给1到10分，各附一句理由并指出行号。
然后阅读 <W/runs/s0> 下各条测试的transcript.md，列出agent实际出问题的地方：哪一步走错、SKILL.md里哪句话没被照做、哪里绕了路。每条写明测试id和对应的SKILL.md行号。
不要建议删除角色定位和交付标准这类身份层段落。
把结果写进 <W/e1.md>，最后只回复我各维度分数一行。
```

## 触发测试

用途：检查description能不能把该来的请求引来、把不该来的挡在外面。skill-creator的触发评测只看目标skill自己；这里把邻居skill一起放进去，因为真实环境里抢请求的正是它们。

1. 写8到10条请求，存目标skill目录的`trigger-tests.json`：
   ```json
   [{"query": "用户原话", "should_trigger": true},
    {"query": "相邻但不该由它处理的请求", "should_trigger": false}]
   ```
   该触发和不该触发各半。该触发的里面至少两条不含任何触发词，只描述需求；不该触发的要选真正相邻的任务，最好是某个邻居skill的本职。
2. 准备skill清单：目标skill加上同一环境里安装的其他skill的name和description（数量多时取10到20个，必须包含职责最接近的几个）。打乱顺序。
3. 每条请求派一个独立agent（或一个agent逐条处理，但每条之间不给反馈）：
   ```
   下面是当前可用的skill清单（名称：说明）：
   <清单>
   用户说：「<query>」
   你会加载哪个skill来处理？只回答skill名称；觉得都不需要就回答「无」。
   ```
4. 统计：该触发的命中率、不该触发的误触率。命中低于八成或有误触，就改description。
5. 改description也要防过拟合：把请求分成两半，只看前一半的失败来改，用后一半验证。
6. 裁决：后一半请求上，命中率上升或误触率下降，且另一项没有变差 → 保留新description；否则回滚。结果记进results.tsv，`eval_mode`填`trigger`，`new_score`填「命中x/y，误触m/n」。description的改动只走这条通道，不走产出盲评。

这是模拟测试，属于E2里较弱的一种。runtime支持真实加载统计时，以真实加载为准。

## 六个会把结论测反的陷阱

| 陷阱 | 后果 | 防法 |
|---|---|---|
| 对照组产出放在被测agent看得见的目录 | 被测agent读了对照稿，产出里出现大段逐字重合，盲评作废 | 各组目录互不可见；prompt禁止列目录；怀疑时比对两份产出的长句重合 |
| 裸跑组其实不裸 | runtime自带的内置skill顶替了被测skill的功能，对照组被抬高 | 开测前看一眼runtime内置了哪些skill；对照组不纯就在报告里写明 |
| 评委把随skill分发的脚本当成虚构 | 自带脚本的skill被冤枉，纯方法论skill显得更可靠 | 给核实型评委skill目录路径：本机找不到先去那里找 |
| A/B顺序固定 | LLM评委有位置偏好，总偏向先看到的那份 | 用pair逐评委逐测试随机顺序 |
| 产出里留着来历线索 | 执行记录和文件里的路径会暴露哪份带skill、哪份是新版，盲评失效 | pair去掉执行记录、抹掉路径；测试文件不进skill快照 |
| 单次运行当定论 | agent同一任务重跑结果就会波动，一条测试的胜负可能只是运气 | 胜负只差一条且评委有分歧时，那几条两版各重跑一次 |

## 没有python3时的手工体检清单

逐条检查，命中的记下来，口径同脚本：

- 错误：没有frontmatter；缺name或description；description超过1024字符；正文里有密钥。
- 警告：description少于30字符或没写何时用；description用第一、第二人称；正文超过500行；SKILL.md提到的references、scripts、assets文件不存在；有个人目录的绝对路径；破坏性命令附近没有确认或禁止说明。
- 提示：references里有SKILL.md没提到的文件；绑定单一runtime的措辞；未完成标记；软化措辞3处以上；没有测试集或没有留出集。
